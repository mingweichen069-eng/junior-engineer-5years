## 1. 一句话

你是一家小公司刚入职的初级后端工程师。没有人给你标准答案，系统也不会在你点错时弹出红叉——它只会在大促那天，用一次真实的故障告诉你，上个月那个"先加个缓存顶一下"的决定到底值不值。

---

## 2. 设计支柱

按优先级排序；发生冲突时，序号小的赢。

1. **因果必须可推演。** 任何一个数字变化，玩家都能在界面上追溯到"哪条规则、哪次操作、哪一周"造成的。做不到溯源的效果，一律砍掉。
2. **没有免费的最优解。** 每个方案都要在至少一个维度上付出代价，且代价是玩家能感知的（钱、时间、风险、人的情绪、未来的自由度）。
3. **信息本身是资源。** 玩家不是"不知道答案"，而是"不知道该看哪里"。监控、日志、文档、同事关系，都是要花行动点去换的情报。
4. **世界不为玩家暂停。** 你不处理，债务照样计息，用户照样增长，磁盘照样变满。
5. **低成本是设计约束，不是妥协。** 单屏、纯 CSS、零美术资源也能做出信息密度。

## 3. 玩家幻想

> "我不是在背八股。我是那个在会议室里说'先别扩容，我先看一眼慢查询'，然后真的把问题定位出来的人。"

玩家想要的四件事，按获得顺序：

| 阶段 | 玩家想要 | 游戏如何满足 |
|---|---|---|
| 0–2 周 | 别背锅 | 故障有前因，能查到源头，能写复盘 |
| 1–3 月 | 被看见 | 绩效、主管评价、晋升评审 |
| 3–6 月 | 掌控系统 | 从"救火"到"提前三个月预判容量" |
| 6 月+ | 被信任 | 拿到架构决策权，能够说"不" |

反面幻想（明确不做）：不做全栈救世主，不做 CEO，不做黑客，不做 996 英雄。你是一个有边界、有上级、有预算限制的工程师。

## 4. 核心循环

### 4.1 周循环（主循环，24 回合 = 6 个月）

```
┌─ 周一早晨 ────────────────────────────────────────┐
│ 收到 1~3 条新信息（工单 / 群消息 / 周报 / 告警）    │
│ 看到上周结算后的系统状态（延迟、错误率、磁盘、现金）│
└──────────────────┬────────────────────────────────┘
                   ▼
        分配 5 点行动力（AP）
                   │
    ┌──────────────┼──────────────┬─────────────┐
    ▼              ▼              ▼             ▼
  交付任务      技术操作        调查/学习      沟通/组织
  (换绩效)     (改系统)       (换信息)       (换信任)
    └──────────────┴──────────────┴─────────────┘
                   ▼
              推进一周
                   ▼
   模拟 7 天：流量 → 负载 → 数据库 → 应用 → 用户 → 收入
                   ▼
        事件判定 → 生成周报 / 月报
```

**为什么是周**：月太长，故障没有"发酵"的空间；日太碎，每次点击的信息增量太小。周是"一次决定、一次反馈"的最小自然单位。每月固定 4 周、每年 48 周，去掉闰年和大小月，保证任何一次存档都能被精确复算。

### 4.2 月循环
- 第 4 周结束时自动结算：财务报表、SLA、绩效初评、技术债计息。
- 月度报告是**叙事的重心**：用一段人话总结这个月发生了什么（模板生成，可选 AI 润色），数字全部来自状态，不允许模型编造。

### 4.3 半年循环
- 第 6 月：晋升评审（P4 → P5）。
- 第 12 月：A 轮尽调 / 年度复盘，决定结局分支。
- 五年是完整游戏的长度；**第一版只做第 1 年，MVP 只做前 6 个月**。

### 4.4 一条必须跑通的因果链

这是 MVP 的验收主线，每一环都由规则算出，环环相扣：

```
注册 18 万 → 24.3 万（+35%）
   → DAU 2.4 万 → 3.2 万
   → 高峰 QPS 78 → 105
   → 订单表 120 万 → 138 万行，Q1 查询 3.05 QPS
   → Q1 单次 121ms → 301ms（磁盘排队从 0.95ms/IO 涨到 4.02ms/IO）
   → 磁盘 IOPS 占用 74% → 92%
   → 接口 p95 136ms → 316ms，出现超时
   → 客服工单 +40%，转化率 −2%，churn +0.8%
   → 收入下降、SLA 逼近 99.5%
   → 主管评价下降，晋升评审受影响
```

玩家在链条的任意一环介入，都会改变后面所有环节。他也可以选择**不介入**，看着它一路走到大促。

## 6. 资源

五种资源，每种都有"获取方式"和"耗尽后果"：

| 资源 | 初始 | 获取 | 耗尽 |
|---|---|---|---|
| **行动力 AP** | 5/周 | 加班（-精力）、拒绝需求（-主管好感） | 事情做不完，任务逾期 |
| **现金** | ¥50 万 | 收入、融资 | 发不出工资 → 裁员 → 结局 |
| **精力** | 80/100 | 休息、准点下班 | 失误率上升、健康事件、离职冲动 |
| **信誉（公司内）** | 50/100 | 交付、救火、复盘 | 没人信你，预算批不下来，绩效降档 |
| **信息** | 极低 | 监控、日志、读代码、问人、读文档 | 只能猜，猜错就是事故 |

**关键**：AP 是唯一的硬约束，但它不是"金币"。你不能靠刷副本来获得 AP，只能靠加班（有代价）或更好的规划（省下来）。这是本作和"答题换金币"最本质的区别。

## 8. 渐进式技术操作：四层

这是全局最重要的教学结构。注意：四层不是"关卡"，而是**同一件事的四种表达深度**，玩家可以随时上下切换。

### 第一层：自然语言目标
> "商家反馈：早上打开'我的订单'要转好几秒。"

- 玩家只能看到现象、投诉、报表。
- 可执行的动作是"调查"：看监控、翻代码、问人、读文档。
- **这一层不教任何技术**，只制造"我想知道为什么"的动机。

### 第二层：组件操作
- 按钮级：`添加索引` / `改写查询` / `加缓存` / `调连接池` / `加服务器` / `加只读副本`。
- 每个按钮都显示**预估影响区间**（不是精确值），例如"预计扫描行数从 120 万降到 20，预计写入延迟 +0.2ms"。
- 预估有误差（±30%），因为真实世界没有精确预估。误差本身是玩法。

### 第三层：参数与结构
- 索引选哪几列、什么顺序；缓存 TTL 与失效策略；连接池大小与超时；隔离级别；分页方式。
- 这一层开始出现"看起来都行、实际差别巨大"的选择：
  - `(user_id, created_at)` vs `(created_at, user_id)`；
  - TTL 30s vs 300s；
  - 连接池 40 vs 100；
  - `LIMIT OFFSET` vs 游标分页。

### 第四层：真实技术操作
- 打开 SQL 编辑器，写真正的 SQL，在**真实 SQLite 副本**上执行，看真实的 `EXPLAIN QUERY PLAN`、真实行数、真实耗时。
- 通过校验后可以"发布到生产"（生产仍是模型，但玩法是真实的）。
- 后续扩展：写 Flask 路由、写 Dockerfile。第一版只做 SQL。

### 解锁规则（不做等级墙）

| 层 | 解锁条件 | 设计意图 |
|---|---|---|
| 1 | 默认 | — |
| 2 | 默认 | 让新人第一天就能动手 |
| 3 | 完成任意 1 次技术操作，或读 2 篇内部文档 | 用"做过"换"看得更深" |
| 4 | SQL 技能 ≥ 30（约 6–8 次相关行动），**或**开局勾选"老手模式" | 不让新人面对空白编辑器，也不让会 SQL 的人被当傻子 |

> 老手模式：跳过前两层的引导，直接开放第三、四层，并把初始 SQL 技能设为 55。这一条是专门为你（已有 Flask + MySQL 基础）准备的。

## 9. 因果设计：四个示范决策

以下四个案例是**验收时必须能复现**的。每个都给出真实机制、代价和二阶后果。

### 9.1 案例 A：老板的大屏（开局事件）

**现象**：每天 9:00–11:00，全站接口变慢，老板办公室墙上的大屏转圈。

**真实机制**：大屏每 10 秒刷新一次，SQL 是：

```sql
SELECT COUNT(*), SUM(amount)
FROM orders
WHERE DATE(created_at) = CURDATE()      -- 函数包住索引列，索引失效
  AND status IN (1,2,3);
```

`DATE(created_at)` 让 MySQL 无法使用 `idx_orders_created`，退化为全表扫描 120 万行。单次 850ms，3 个客户端每 10 秒刷新、偶尔还有手动刷新，合计约 0.35 QPS，持续把云盘打到 74% IOPS。磁盘排队延迟会传染给所有查询。

**四种解法，没有唯一正确答案**：

| 方案 | 成本 | 收益 | 二阶后果 |
|---|---|---|---|
| 给大屏加 30s 缓存 | 1 AP，+¥0 | 数据库负载 ↓ 90% | 数据最多旧 30 秒；如果 TTL 设成 3600s，老板看到一小时前的营收，信任 -10 |
| 改写 SQL 为区间查询 | 2 AP，需要 SQL 技能或第三层参数 | 850ms → 1ms | 根治，且以后所有报表都受益；但需要改代码 + 发布，有回归风险 |
| 加只读副本 | 2 AP + ¥3000/月 | 隔离大屏 | 全表扫描的成本还在，只是搬到了副本；副本延迟会让报表更难对账 |
| 建汇总表 + 定时任务 | 3 AP | 一劳永逸 | 引入定时任务和数据一致性维护，多一个可能失败的环节 |

**关键**：四种都能"解决"问题，但只有一种能让玩家在三个月后**不用再回来处理同一个问题**。这个判断不能靠背，只能靠看懂 `EXPLAIN` 和 IOPS 曲线。

### 9.2 案例 B：索引的代价

玩家给 `orders` 加 `(user_id, created_at)`：

- 查询 `WHERE user_id=? ORDER BY created_at DESC LIMIT 20`：120 万行 → 20 行，121ms → 4ms。
- 代价 1：磁盘 +33MB（看似可忽略，但订单涨到 500 万行时是 +140MB，且需要重建）。
- 代价 2：每次下单多维护一棵 B+ 树，写入 +0.18ms。
- 代价 3：**建索引本身可能锁表**。120 万行用朴素 `ALTER TABLE` 约 40 秒；这 40 秒内的下单请求会堆积。如果挑在晚高峰做，就是一次小型事故。用 `ALGORITHM=INPLACE, LOCK=NONE` 可以不阻塞写入，但构建时间更长、IO 占用更高。
- 代价 4：索引不是越多越好。加满 5 个索引后，写入延迟从 1.1ms 涨到 2.0ms，磁盘 +200MB，而其中 2 个索引的查询占比不到 3%。

### 9.3 案例 C：缓存的谎言

玩家给"订单状态"接口加缓存，TTL 300s：

- 数据库 QPS ↓ 90%，延迟从 80ms → 2ms。
- 但支付回调是**另一条代码路径**，它直接写库，绕过了缓存失效。约 5% 的订单在支付后仍显示"待支付"。
- 用户点"再次支付" → 重复支付投诉 → 客服工单 +40% → 老板在群里 @ 你。
- 修复方式有两种：补失效逻辑（2 AP，需要看懂两条代码路径），或把 TTL 降到 5s（0 AP，但缓存基本失效，等于白做）。

**这一课的目标**：让玩家自己得出"缓存不是加速，是复制数据；复制就会有不一致"。

### 9.4 案例 D：扩容的边界

大促前，玩家把应用服务器从 6 台扩到 12 台：

- 应用层队列等待 ↓ 90%，但 p95 只从 900ms 降到 820ms。
- 因为瓶颈在数据库，应用层只是在更快地把请求送进数据库。
- 更糟：连接池总连接数翻倍，超过 MySQL `max_connections`，出现 `Too many connections`。

**这一课的目标**：让"加机器"这个最直觉的动作，第一次显得不够用。

## 10. 信息设计：看不见才是玩法

这是本作区别于"技术百科"的核心。

**默认状态下，玩家看不到任何一条查询的耗时。** 界面上只有：
- 接口 p95（聚合值，分不出是哪个接口）；
- 错误率；
- 磁盘、CPU、连接数；
- 客服工单文本。

要看到慢查询，必须花 1 AP 开启慢查询日志 / APM，**并且要等 3 天数据**。这个投资在当期没有任何绩效收益——主管甚至会觉得你在"搞没用的东西"。但它决定了你后面三个月的每一次决策质量。

| 信息源 | 获取成本 | 内容 | 误差 |
|---|---|---|---|
| 客服工单 | 免费 | 现象描述（"订单页转圈"） | 大，可能误导 |
| 应用日志 | 1 AP | 接口级 p95、错误码分布 | 中，看不到 SQL |
| 慢查询日志 | 1 AP + 3 天 | 具体 SQL、扫描行数、耗时 | 小 |
| EXPLAIN | 0 AP（需慢日志） | 执行计划、用没用索引 | 无 |
| 同事 | 1 AP + 关系 | 历史背景、谁写的、为什么这么写 | 有立场偏差 |
| 内部文档 | 1 AP | 原理（可迁移） | 可能过时 |
| 代码 | 0 AP | 真相 | 需要读得懂 |

**设计约束**：所有信息都有获取成本，且没有一条信息能单独给出答案。玩家必须交叉验证。比如客服说"订单页慢"，慢日志显示慢的是"运营报表"，代码显示报表被大屏每 10 秒调用一次——三个信息拼起来才是真相。

## 11. 事件系统

### 11.1 三类事件

| 类型 | 触发 | 占比 | 作用 |
|---|---|---|---|
| **后果事件** | 状态条件满足（如 p95 > 800ms 持续 2 周） | 60% | 让玩家的决策产生后果，可预期 |
| **外部事件** | 定时 + 世界状态（大促、竞品、融资窗口） | 25% | 打破平衡，防止一套打法通吃 |
| **人物事件** | 员工满意度、关系值、工作量 | 15% | 把技术问题变成组织问题 |

**禁止**：完全随机、与状态无关的"天灾"。每个事件必须能回答"为什么是这周"。

> **v0.2 修订**：事件不再是周末轮询出的状态快照，而是由规则在周内某一天显式触发、可沿因果链传播（`cause` → 子事件）。周内分段、事件总线与传播上限见 [DESIGN_ADDENDUM.md](DESIGN_ADDENDUM.md) §2。

### 11.2 事件必须可追踪

每个事件在界面上都有"触发原因"展开项，显示：

```
事件：老板在群里问"大屏怎么又卡了"
触发条件：
  ✓ dashboard.p95_ms = 852 > 800（连续 2 周）
  ✓ boss.trust < 60
  ✗ user_growth > 10%/月（未满足）
权重：3.0（基础 1.0 + 条件加权 2.0）
冷却：4 周
上一次触发：第 2 周
```

这是硬性要求：玩家复盘时能查，开发者调参时能查，测试时能断言。

### 11.3 事件样例（MVP 的 8 个）

| ID | 名称 | 触发条件 | 玩家可做的选择 |
|---|---|---|---|
| E01 | 大屏又卡了 | 大屏 p95 > 800ms ×2 周 | 缓存 / 改 SQL / 加副本 / 拖着 |
| E02 | 早高峰雪崩 | 磁盘 IOPS > 95% 且持续 1 周 | 降级 / 限流 / 紧急扩容 / 硬扛 |
| E03 | 支付状态不对 | 缓存 TTL > 30s 且存在绕过失效的写路径 | 补失效 / 降 TTL / 关缓存 |
| E04 | 新功能上线失败 | 无测试 + 交付周期压缩 | 回滚 / 热修 / 让前端背锅（关系 -） |
| E05 | 老陈要离职 | 满意度 < 40 且连续 3 周加班 | 挽留（加薪）/ 交接文档 / 放走 |
| E06 | 大促来了 | 第 4 月定时 | 提前扩容 / 压测 / 什么都不做 |
| E07 | 磁盘 85% | 磁盘使用率 > 85% | 清日志 / 归档 / 扩容 / 删索引 |
| E08 | 老板要"实时数据" | 第 3 月定时 + 大屏改造未完成 | 解释 / 硬做 / 用缓存糊弄 |

## 12. 失败、压力与救赎

### 12.1 死亡螺旋（自然涌现，不脚本化）

```
查询变慢 → 请求占用连接更久 → 连接池耗尽
   → 应用 worker 阻塞 → 队列变长 → 超时
   → 客户端重试 → 流量 ×1.3 → 更慢
```

这是真实系统最常见的崩溃方式。游戏里它由规则自然产生，玩家会亲眼看到 p95 曲线在两周内从 300ms 爬到 5s。

### 12.2 至少三条逃生通道

不允许出现"必死局"。当系统进入螺旋，玩家仍可：

1. **服务降级**：关掉非核心接口（推荐位、排行榜），1 AP，立即释放 40% 负载，但收入 -15%。
2. **只读模式**：禁止下单，保住浏览，减少写锁竞争，可用性数字好看但订单归零。
3. **花钱买命**：联系云厂商紧急升配，¥20,000，10 分钟生效（模拟上是一周），现金压力巨大。

### 12.3 结局（第一版 3 个）

| 结局 | 条件 | 基调 |
|---|---|---|
| **A 轮通过** | 第 12 月：注册 ≥ 35 万、月收入 ≥ 60 万、可用性 ≥ 99.5% | 你成为 P5，开始带一个小系统 |
| **被收购 / 裁员** | 处境分 < 25，且已进入预警 ≥ 2 周（见补充说明 §3） | 公司还在，但你被优化了；展示履历和复盘 |
| **技术破产** | 可用性 < 98% 连续 2 月 或 数据丢失 | 公司失去核心客户，项目终止 |

失败后不是"重开一局"，而是进入**复盘模式**：逐周回放关键决策，显示"如果当时……"的对照模拟（用同一套规则重跑，不是编故事）。这是本作最有教育价值的部分之一。

## 13. 职业线（刻意做薄）

第一版**不做**技能树、不做转职、不做副业。只做三件事：

1. **技能熟练度**（SQL / 数据库 / 后端 / 运维 / 设计）：只影响"你能看懂多深"和"解锁第四层"，不影响数值倍率。
2. **月度绩效**：交付 40% + 稳定 30% + 技术影响 20% + 协作 10%。主管有偏好权重（周明远偏稳定，王总偏交付）。
3. **履历时间线**：自动把玩家做过的事写成条目（"第 3 周：定位并修复大屏全表扫描，p95 从 852ms 降至 4ms"）。这是给玩家的"作品集"，也是结局时的总结。

> 五年是完整游戏的野心。第一年只需要让玩家相信"再干一年，我会更值钱"。

## 14. 反"答题软件"自检表

每一条都是硬性验收项，不达标就不算完成：

- [ ] 游戏里没有任何一道选择题、填空题、判断题。
- [ ] 没有任何"答对 +10 经验"的奖励。
- [ ] 玩家不做任何事，世界也会变化（债务计息、用户增长、磁盘变满）。
- [ ] 同一个问题至少有 2 种可行解法，且各有明确代价。
- [ ] 存在"看起来对、实际错"的操作（如给低选择性列建索引、TTL 设太长）。
- [ ] 存在"短期正确、长期错误"的操作（如用缓存掩盖 SQL 问题）。
- [ ] 技术说明是**可选的**：不读也能玩，读了能玩得更好。
- [ ] 玩家会因为"想知道为什么"而主动打开文档，而不是因为"任务要求"。
- [ ] 所有数值可追溯到规则，没有"AI 说这样比较好"。
- [ ] 失败可复盘，且复盘能指出具体是哪一周的哪个决定导致的。

## 15. MVP 的 6 个月节奏（详细排期见 MVP_PLAN.md）

| 月 | 主题 | 玩家学到的东西 | 核心张力 |
|---|---|---|---|
| M1 | 大屏为什么卡 | EXPLAIN、索引失效、慢查询 | 老板的体感 vs 你的调查时间 |
| M2 | 新功能上线 | N+1、连接池、发布风险 | 交付速度 vs 稳定性 |
| M3 | 拉新后用户 +35% | 容量、索引选择、DDL 锁 | 增长是好事，也是压力 |
| M4 | 大促 | 压测、限流、降级、扩容边界 | 一次性投入 vs 长期成本 |
| M5 | 缓存事故 | 一致性、失效、read-after-write | 性能 vs 正确 |
| M6 | 半年评审 | 技术债、文档、影响力 | 可见的工作 vs 重要的工作 |

## 16. MVP 范围

**做**：单公司、单系统、6 个月、6 类热查询、10 种操作、8 个事件、月度报表、存档、SQL 实验台（只读）。

**不做**（第一版明确砍掉，防止范围爆炸）：
- Redis / Docker / Linux / 微服务（后续扩展）
- 多人、联机、排行榜
- 技能树、转职、副业
- 真实 MySQL 接入（用 SQLite 做实验台，MySQL 用校准模型）
- AI 实时生成剧情（只做可选润色，且可关闭）
- 动画、立绘、音效（最多 3 个 CSS 过渡）

## 18. 第一小时体验（beat sheet）

| 时间 | 发生什么 | 玩家感受 |
|---|---|---|
| 0–2 min | 开场：工位、入职邮件、5 个 AP。左栏灰掉大半，只有"总览/任务/文档"可用 | "东西不多，我能看懂" |
| 2–5 min | 客服工单："商家说早上订单页打不开"。同时老板在群里发了一张大屏转圈的照片 | "好像有两件事，是一件事吗？" |
| 5–10 min | 玩家点"调查"，发现只有聚合 p95，没有明细。花 1 AP 开慢查询日志 | "原来我什么都看不见" |
| 10–18 min | 等 3 天（推进），慢日志出现：`admin_daily_report` 850ms，扫描 120 万行 | "找到了！"（第一次成就感） |
| 18–25 min | 看 EXPLAIN，发现 `DATE(created_at)` 导致 `type=ALL`。文档里搜到"索引失效" | "原来是这么回事" |
| 25–35 min | 选择：加缓存（快、但脏）或改 SQL（慢、但根治）。第一次真正的取舍 | 犹豫 → 决策 → 紧张 |
| 35–45 min | 推进一周，p95 下降，但老板说"数字好像没更新" | "哦，缓存有代价" |
| 45–60 min | 月末报表：SLA 99.3%，绩效 B。主管说"下个月把新功能做了" | "我知道我错过了什么" |

**关键设计**：第一个小时里，玩家没有答过一道题，但已经完整经历了一次"观察 → 假设 → 取证 → 决策 → 承担后果"。

## 19. 需要你拍板的设计选择

1. **主循环粒度**：周（推荐）还是月？周的信息密度更高，但 24 回合的操作量更大。
2. **开局难度**：M1 的大屏是"很慢但能用"（推荐，有缓冲）还是"每天超时"（更刺激，但新手可能直接崩）。
3. **AI 叙事**：默认关闭、手动开启（推荐），还是默认开启、可关闭？
4. **第四层解锁**：按技能门槛（推荐）还是第一周就全开？
5. **结局数量**：第一版 3 个够不够，还是只做"A 轮通过"一个正结局 + 一个失败结局？
