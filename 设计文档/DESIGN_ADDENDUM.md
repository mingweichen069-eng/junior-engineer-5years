## 1. 问题：轮询式事件为什么不够

现有实现（GDD §11、TDD §5.3 的 S13）是「周末统一判定」：条件读取的是**本周结算之后**的状态。

三个具体毛病：

1. **时序错位。** 玩家在周三执行了锁表的 `ALTER`，事件却要等到周日才生成。故障已经发生，世界却还没反应。
2. **因果断裂。** 客服工单、主管信任这些下游变化，看到的是「工单数 > 阈值」这类条件，而不是「因为锁表」。玩家复盘时无法归因。
3. **无法表达连锁。** A→B→C 本该是一条链，现在被拆成三次独立判定，权重互相污染，也无法保证顺序。

一句话：现在产生的是**状态快照 + 概率**，不是**事件**。

## 2. 方案：周内分段 + 事件总线 + 有界传播

### 2.1 三个时钟

| 时钟 | 用途 | 精度 |
|---|---|---|
| 周（对外） | 玩家操作与结算的回合 | 1 周 |
| 天（对内） | 事件时间戳、故障持续、分段结算 | 1 天（每周 7 段） |
| 即时（链内） | 同一条链的传播顺序 | 同一天，按序号 |

玩家仍然一周只点一次，但引擎知道「这周三下午」。

### 2.2 周内分段结算

一周按事件发生的天切成若干段：

```
D1–D2 正常  →  D3 锁表 40s  →  D4–D7 恢复
```

- **计数类**（错误数、工单数、失败订单）：按段求和。
- **比率 / 延迟类**（p95、可用性）：取最差段，并记录「受影响天数」。
- 周报同时显示「整周」与「最差一天」，避免尖峰被平均掉。

```
metric_week   = Σ (segment_days / 7) × rate_segment      # 计数类
p95_week      = max(segment_p95)                          # 延迟类
affected_days = Σ segment_days where segment ≠ baseline
```

### 2.3 事件总线

事件不再从状态里「扫」出来，而是由规则模块显式触发：

```python
bus.emit(
    "E02_ddl_lock",
    cause=None,             # 根事件没有父节点
    day=3,                  # 周三
    payload={"lock_seconds": 40, "blocked_writes": 1240},
)
```

总线按 `(day, priority, seq)` 排序逐个解析。每个事件解析后可以继续触发子事件，`cause` 指向父事件 id——日志天然是一棵树。

### 2.4 有界传播

链式事件最大的风险是失控。四道上限：

| 限制 | 值 | 目的 |
|---|---|---|
| 单链最大深度 | 3 | 锁表 → 写失败 → 工单 → 信任，到此为止 |
| 每周链事件总数 | 6 | 防止一次故障刷出几十条 |
| 同一事件冷却 | 2 周 | 防止同一个剧本反复上演 |
| 单事件状态改动上限 | 配置项 | 防止一次扣 50 点信任 |

超限时写一条 `chain_truncated` 日志，而不是静默丢弃——复盘时要能看见「链被截断了」。

确定性：随机数用 `rng(seed, week, f"{event_id}:{depth}")` 生成，与处理顺序无关。

### 2.5 两遍结算

```
P1  基线模拟（流量 / 数据库 / 应用）
P2  事故检测（从指标生成根事件）
P3  链式解析（事件总线，含状态改动）
P4  脏重算（只重算被标记的聚合，最多 1 遍）
P5  组织 / 经济 / 绩效
P6  快照与事件 DAG 落盘
```

P4 是关键：锁表改变了本周错误率，重算后 p95、SLA、工单数**当周**就变，不用等下周。

### 2.6 事件日志变成 DAG

```
W3 D2 14:03  DDL 锁表（玩家操作，naive ALTER）
  └─ W3 D2 14:03  下单写入失败 1,240 次
      ├─ W3 D2 15:10  客服工单 +180
      └─ W3 D3 10:00  主管信任 −8
```

复盘页按缩进树展示，每条带时间戳、因果 id、状态改动前后值。这比现在的平铺列表更能回答「到底是谁害的」。

### 2.7 延迟不是取消，是显式

有些后果本来就该慢：信任、离职、融资。用 `delay_days` / `delay_weeks` 声明，UI 标注「预计 W4 生效」。

规则：**技术后果默认 0 延迟；人的后果允许延迟，但必须写进日志。**

### 2.8 配置示例

```yaml
- id: E02_ddl_lock
  when: {op: ddl_started, lock_mode: naive, peak: true}
  effects:
    - {op: block_writes, seconds: "$build_seconds"}
  emit:
    - {id: E02_write_fail, delay_days: 0}

- id: E02_write_fail
  effects:
    - {op: add, key: orders.failed, value: "$blocked_writes"}
    - {op: add, key: support.tickets, value: "$blocked_writes * 0.02"}
  emit:
    - {id: E02_manager_heat, delay_days: 1}

- id: E02_manager_heat
  effects:
    - {op: add, key: org.manager.trust, value: -8}
    - {op: add, key: player.stress, value: 10}
```

权重只用于**根事件**的抽取；链内子事件由父事件决定，不参与抽样。

## 3. 裁员：不是事件，是处境

### 3.1 为什么不能做成线性事件

「现金 < 0 → 裁员」有两个问题：玩家觉得是突然死亡；现实中裁员是多项指标一起烂掉之后才发生的。

所以做成**累积分数 + 状态机**，而不是一次判定。

### 3.2 处境分

```
S = 100
  − 30 × clamp((12 − runway_weeks) / 12, 0, 1)
  − 25 × clamp((99.5 − availability_mtd) / 1.5, 0, 1)
  − 20 × clamp((3.5 − perf_avg) / 2, 0, 1)
  − 15 × clamp((60 − manager_trust) / 60, 0, 1)
  − 10 × layoff_wave_pressure            # 公司层面，由外部事件驱动
```

权重可以调，但**四项分项必须在 UI 上可见**。玩家要能看到自己是在「现金」上失血，还是在「信任」上透支。

### 3.3 四档状态机（带迟滞）

| 档位 | 分数 | 玩家感知 | 出口 |
|---|---|---|---|
| 安全 | S ≥ 60 | 无 | — |
| 观察 | 40 ≤ S < 60 | 主管问进度更频繁；HR 发组织调整邮件 | 回安全 / 掉预警 |
| 预警 | 25 ≤ S < 40 | 主角独白 + 主管 1:1 明说 | 4 周挽救窗口 |
| 名单 | S < 25 | HR 约谈 | 2 周内无改善 → 裁员结局 |

三条硬规则：

1. 每档至少停留 **2 周**，一次只降一档（迟滞，防止分数抖动导致闪断）。
2. 必须先经过**预警 ≥ 2 周**，才可能进入名单。
3. 现金 > 6 个月且可用性正常时，S 不会低于 40（硬保护）。

### 3.4 预警由主角说出来

不弹「系统警告：你将被裁员」，而是按档位给三种独白：

> **观察**：周明远最近找我聊了两次进度，语气比平时客气。我不太喜欢这种客气。

> **预警**：我下班后开始刷招聘网站。不是因为想走，是因为不知道下个月还在不在。

> **名单**：HR 约我周四下午三点，会议室 B。我知道那个会议室是干什么用的。

每段独白旁边配一张「处境卡」：现金还能撑几周、可用性差多少、绩效几档、主管信任多少。

### 3.5 挽救窗口

预警触发时，给一个**明确、可达成**的目标（按当前短板三选一）：

- **稳定**：把月可用性拉回 99.5%。
- **现金**：把月成本砍 20%（裁员 / 降配 / 砍营销）。
- **增长**：拿下 A 轮意向（注册与收入达标）。

4 周内达成 → 回到观察档；未达成 → 进入名单。

### 3.6 结局优先级

同一周触发多个结局时，按严重度取一个：

```
技术破产  >  裁员  >  A 轮通过
```

复盘页要说明「另一条路径只差多少」——这是失败之后最有价值的信息。

## 5. 对 MVP 的影响

- **工作量**：+2 天（M3 事件总线与分段 +1，M6 结局与复盘 +1），总计 21 天。
- **新增测试**：
  - 锁表链在同一周内完成 4 跳，且深度 ≤ 3。
  - 每周链事件 ≤ 6，超限必须留下 `chain_truncated`。
  - 裁员必先经过预警 ≥ 2 周。
  - 现金 > 6 个月时不会被裁。
  - 同一存档重放，事件 DAG 完全一致。
- **风险**：链式事件容易数值爆炸。用 §2.4 的上限 + 不变量测试兜底。

## 6. 新增验收项

1. 玩家周三执行 `ALTER TABLE`，**当周**报表就能看到写入失败与工单上涨，不用等下周。
2. 复盘页能把「锁表 → 写失败 → 工单 → 信任」画成一棵树。
3. 被裁员前，玩家至少收到过一次主角口吻的预警，并拥有完整的 4 周挽救窗口。
4. 处境面板的四项分项与总分可复算。
5. 三个结局都能在 20 个种子的扫描里被触发。
