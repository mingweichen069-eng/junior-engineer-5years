# MVP 开发计划

| 项 | 内容 |
|---|---|
| 版本 | v0.1 |
| 目标 | 6 个月（24 周）可完整游玩的数据库维护原型 |
| 规模 | 约 21 个工作日（含 v0.2 连锁事件 +2 天） |
| 前置 | 本文档末尾 5 个决策点确认后开工 |

---

## 1. MVP 要证明什么

不是"功能齐全"，而是回答一个问题：

> **一个不懂数据库的人，能不能在没有任何题目和积分的情况下，因为想把工作做好，自己搞明白索引、缓存和连接池？**

对应的验收（每一条都要能演示）：

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | 新人能理解目标 | 让一个人只看界面玩 15 分钟，能说出"我要让订单页变快" |
| 2 | 能通过尝试理解机制 | 加索引前后，界面上的扫描行数、磁盘、写入延迟都有可解释的变化 |
| 3 | 决策改变世界 | 两条不同路线跑 24 周，结局指标显著不同 |
| 4 | 有成本收益权衡 | 每个动作至少有一个负面指标 |
| 5 | 有意料之外但合乎规则 | 无监控 + 大促 = 雪崩；缓存 + 支付回调 = 客诉 |
| 6 | 会主动看文档 | 不读文档也能通关，但读过的玩家平均绩效高 15% 以上 |
| 7 | 知识可迁移 | 玩家能在 SQLite 实验台写出正确的区间查询并看懂 EXPLAIN |
| 8 | 无考试也能持续玩 | 6 个月流程里没有任何选择题 |

## 2. 范围

### 2.1 必须做（P0）

- 单一公司、单一系统、24 周、1 个存档槽 + 自动存档
- 6 条热查询、4 张表、索引/缓存/连接池/扩容 4 类操作
- 每周结算、每月报表、8 个事件、技术债、基础组织与财务
- SQLite 实验台（只读 SELECT）
- 单屏 UI + 8 个面板 + 2 张图表
- 确定性 + 存档 + 回放 + 25 个以上测试

### 2.2 应该做（P1，时间够就做）

- 只读副本
- 事件复盘页
- 导出 CSV
- 老手模式
- 3 个结局

### 2.3 明确不做（P2，进第二版）

- Redis / Docker / Linux / 微服务
- 多人、排行榜、成就
- 真实 MySQL 运行时依赖
- 任意 Python 代码执行
- 动画、立绘、音效
- 移动端

## 3. 里程碑

> 每个里程碑结束都要有一个**能跑的东西**，而不是"写完了但还不能用"。

### M0 · 骨架（1 天）

**产出**
- 目录结构、`pyproject.toml`、pytest 配置
- `core/model/state.py`：全部 dataclass + `to_dict/from_dict`
- `new_game(seed, difficulty)`：生成初始状态
- `services/save.py`：SQLite 存档、读档、槽位
- `tools/refcalc.py` 移植为 `core/rules/constants.py`

**验收**
- `py -3 sim_cli.py new --seed 42` 打印初始状态
- 存档 → 读档 → 状态哈希一致
- `pytest` 全绿（此时只有 3 个测试）

### M1 · 数字会动（3 天）

**产出**
- `traffic.py`：DAU、QPS、请求构成
- `storage.py`：页数、磁盘、命中率
- `query.py` + `optimizer.py`：访问路径枚举、成本计算
- `pool.py` / `app_queue.py`：Erlang-C 排队
- CLI `py -3 sim_cli.py sim --weeks 24 --no-events`：输出每周指标表

**验收**
- CLI 输出的 M1 数字与 [SIMULATION_RULES.md](SIMULATION_RULES.md) §17 一致（误差 < 2%）
- 单元测试：成本单调性、命中率边界、Erlang-C 收敛
- 能画出"用户 +35% → p95 上升"的曲线（终端 ASCII 即可）

### M2 · 循环闭合（3 天）

**产出**
- `engine.step(state, actions)`：按 S1–S15 顺序实现
- `settle_month()`：月报快照
- `history`：每周指标、事件、决策
- 黄金用例：seed 42 + 固定操作 → 24 周哈希

**验收**
- 不改操作，连续推进 24 周不崩溃
- 同一输入两次运行哈希一致
- 月末报表数字与每周快照汇总一致

### M3 · 有得选（4 天）

**产出**
- `content/actions.yaml`：10 个动作
- `core/rules/events.py` + `content/events.yaml`：8 个事件
- **事件总线**：`emit / cause / day / depth`，周内按天分段
- `debt.py` / `org.py` / `economy.py` / `career.py`
- AP 校验、前置条件、延迟生效

**验收**
- 每个动作都能被拒绝（AP 不够 / 钱不够 / 前置不满足），且提示原因
- 8 个事件在 20 个种子的扫描里至少各触发 1 次
- 锁表链在同一周内跑完 4 跳，深度 ≤ 3，事件数 ≤ 6
- 负债计息、满意度、离职判定可复算

### M4 · 能点了（4 天）

**产出**
- Flask 入口、`/api/state`、`/api/action`、`/api/advance`
- Jinja 骨架 + 顶栏/左栏/右栏/底栏
- 面板：总览、数据库、架构、任务、团队、财务、技术债、文档、事件、履历
- Chart.js：p95 趋势、现金曲线
- 操作确认弹窗（显示预估影响与代价）

**验收**
- 不刷新页面完成一次"调查 → 加索引 → 推进 → 看结果"
- 所有数字有 tooltip 指向规则
- 1280×720 下不出现横向滚动

### M5 · 能实验（3 天）

**产出**
- `lab/replica.py`：生成 20 万行副本
- `lab/sandbox.py`：只读、超时、白名单
- `lab/explain.py`：解析 `EXPLAIN QUERY PLAN`，生成 warnings
- `/api/lab/query`、`/api/lab/deploy`
- 发布流程：实验验证 → 结构化变更 → 生产生效

**验收**
- 写 `SELECT * FROM orders WHERE user_id=1` 能看到 `SCAN` 警告
- 写 `DATE(created_at)` 查询能看到 `SCAN`，改成区间能看到 `SEARCH`
- 危险语句（ATTACH / PRAGMA / 多语句）被拒绝
- 超时查询 3 秒内中断，主进程不受影响

### M6 · 能玩（3 天）

**产出**
- 数值平衡：5 种策略 × 20 种子扫描
- 新手引导（3 条提示，不强制）
- 结局判定（含处境分状态机与裁员预警）+ 复盘页（事件 DAG 树）
- README、启动脚本

**验收**
- 见 §6 的平衡实验
- 从新游戏到第 24 周，无报错、无 NaN、无死局
- 一局完整游玩 45–90 分钟

| 动作 | AP | 钱 | 主要效果 | 副作用 |

| 改写 SQL | 2 | 0 | 根治 | 需要技能 / 发布风险 |

| 调 TTL | 0 | 0 | 平衡新旧 | 两头都有代价 |
| 调连接池 | 1 | 0 | 减少等待 | 超上限直接拒绝 |
| 加应用服务器 | 1 | ¥1,200/月 | 应用容量 | 不解决 DB；连接数增加 |
| 加只读副本 | 2 | ¥3,000/月 | 读扩展 | 复制延迟、对账困难 |

## 6. 平衡实验协议

不做"我觉得平衡了"，用脚本跑。

### 6.1 五种策略

| 策略 | 行为 |
|---|---|
| S1 救火型 | 只处理事件，不主动优化 |
| S2 索引狂 | 见查询就加索引 |
| S3 缓存党 | 一切靠缓存 |
| S4 扩容党 | 见慢就加机器 |
| S5 均衡型 | 监控 → 定位 → 最小修复 → 补文档 |

### 6.2 方法

```
for seed in 20 个种子:
    for strategy in 5 种策略:
        headless_run(strategy, seed, weeks=24)
        记录：结局、现金、p95、可用性、绩效、技术债
```

### 6.3 判定标准

- 没有任何策略胜率 > 70%。
- 每种策略都至少在一个种子上失败（说明有真实风险）。
- S5 的平均绩效最高，但**不是每个种子都最高**（否则又变成唯一解）。
- S1 不能"躺赢"（说明世界在动）。
- S3 应在 2–3 个种子上因一致性问题翻车。

### 6.4 如果出现单一最优解

优先加"约束"而不是"削弱"：

- 加预算上限；
- 加组织阻力（主管不批）；
- 加信息不对称（看不到效果）；
- 加时间窗口（来不及）。

## 10. 已确认的 5 个决策

**状态：2026-11-18 已确认。** 结论：周循环（24 回合）/ 开局 852ms 不超时 / AI 叙事默认关 / 技能解锁 + 老手模式 / 3 个结局。
连锁事件与裁员状态的补充设计见 [DESIGN_ADDENDUM.md](DESIGN_ADDENDUM.md)。

以下保留当时的选项与理由，便于回看。

1. **主循环用周还是月？**
   我推荐周（24 回合），信息密度和故障发酵都更自然；月制更省操作，但会丢掉"这周先救火还是先做功能"的张力。

2. **开局大屏是"很慢"还是"每天超时"？**
   我推荐"很慢但能用"（852ms，不超时），给新人 2 周缓冲；硬核模式再改成每天超时。

3. **AI 叙事默认开还是关？**
   我推荐默认关、手动开。核心体验不依赖网络和 key，也避免你每次测试都花钱。

4. **第四层（SQL 编辑器）第一周就开，还是按技能解锁？**
   我推荐：普通模式按技能解锁（约 2 个月），并提供"老手模式"开局全开。你已有的基础可以直接选老手。

5. **第一版做几个结局？**
   我推荐 3 个（A 轮 / 裁员 / 技术破产），工作量可控，且能覆盖"成功、经营失败、技术失败"三种教训。

## 11. 开工顺序

确认后我按这个顺序提交，每个里程碑一个可运行的版本：

```
M0 骨架 → M1 数字 → M2 循环 → M3 选择 → M4 界面 → M5 实验台 → M6 平衡
```

每个里程碑结束时我会给你：
- 能跑的命令；
- 一段 30 秒的演示说明；
- 这次改了什么、为什么；
- 已知问题。
