## 0. 约定

### 0.1 单位

| 量 | 单位 | 说明 |
|---|---|---|
| 时间 | 毫秒（ms） | 内部微秒常数用 float，出口 `round(·, 1)` |
| 金额 | 分（整数） | 显示时 ÷100，禁止浮点记账 |
| 数据量 | 页（16KB） | 1 页 = 16,384 字节 |
| 速率 | QPS / IOPS | 每秒请求数 / 每秒 IO 次数 |
| 占比 | 0~1 的 float | 出口 `round(·, 4)` |

### 0.2 取整

- 每一步结束对**比率**取 4 位小数，对**时间**取 1 位小数，对**钱**取整。
- 不在中间步骤随意取整，否则误差会累积。
- 禁止 `NaN` / `inf`：每次除法前判分母，分母为 0 时返回定义好的边界值。

### 0.3 符号

| 符号 | 含义 |
|---|---|
| `N` | 表行数 |
| `P` | 表占用的页数 |
| `S` | 选择率（谓词命中行数 / N） |
| `R` | 扫描行数（rows examined） |
| `B` | Buffer pool 页数 |
| `W` | 工作集页数 |
| `h` | 缓存命中率 |
| `D` | 磁盘 IOPS 需求 |
| `ρ` | 利用率 |
| `λ` | 到达率（QPS） |
| `s` | 单次服务时间（秒） |
| `c` | 并发服务台数 |
| `a` | 爱尔兰负载 `a = λ·s` |

## 1. 日历

```
周 w ∈ {1, 2, 3, ...}
年 Y = ceil(w / 48)
月 M = ((w - 1) mod 48) // 4 + 1
月内周 = ((w - 1) mod 4) + 1
天数 = 7
```

固定 48 周/年、4 周/月、28 天/月。**不做真实日历**。

## 2. 每周结算顺序

严格按序，前一步的输出是后一步的输入：

```
S1  提交操作 → 校验 AP/现金/前置 → 扣资源 → 记录
S2  生效延迟效果（构建完成、监控上线、发布完成）
S3  流量：用户 → DAU → 请求量 → 平均/高峰 QPS
S4  逐查询：选择访问路径 → 计算 CPU/IO/总耗时
S5  聚合数据库：总 QPS、IOPS 需求、CPU 利用、连接并发
S6  缓存：命中/未命中拆分
S7  连接池：排队 → 等待 → 超时
S8  应用：worker 排队 → 接口 p95 → 错误率
S9  可用性：错误分钟、SLA、投诉、订单履约
S10 组织：工作量、满意度、离职判定
S11 技术债：计息、升级、触发判定
S12 经济：收入、成本、现金
S13 事件：条件评估、权重、抽取、排队
S14 快照：写 history
S15 月末：生成月报、绩效初评
```

S4 与 S5 存在循环依赖（成本依赖磁盘排队，排队依赖成本），用**固定 3 轮定点迭代**解决，第 3 轮结果为准。迭代次数固定 → 结果确定。

## 3. 用户与流量

### 3.1 用户

```
DAU = Registered × dau_ratio
dau_ratio = base_dau_ratio × product_factor × reliability_factor
```

| 参数 | 初始值 | 说明 |
|---|---|---|
| `Registered` | 180,000 | 注册用户 |
| `base_dau_ratio` | 0.1333 | 基础日活率 |
| `product_factor` | 1.00 | 每交付一个功能 +0.02，上限 1.15 |
| `reliability_factor` | 1 − 2×月度错误率 | 越不稳定，越少人打开 |

### 3.2 请求量

```
req_per_dau_day = 2.4 × 18 = 43.2
Req_day = DAU × req_per_dau_day
QPS_avg = Req_day / 86400
QPS_peak = QPS_avg × peak_factor
```

| 参数 | 初始值 | 说明 |
|---|---|---|
| `peak_factor` | 6.5 | 晚高峰 / 日均 |
| 大促 `peak_factor` | ×2.2 | 第 4 月，持续 2 周 |

初始：DAU = 23,994，日请求 1,036,541，`QPS_avg = 12.0`，`QPS_peak = 78.0`。

### 3.3 请求构成

| ID | 接口 | 占比 | 类型 | 说明 |
|---|---|---|---|---|
| Q1 | 我的订单 | 1.5% | 读 | `WHERE user_id=? ORDER BY created_at DESC LIMIT 20` |
| Q2 | 运营大屏 | 0.35 QPS 固定 | 读 | 每 10 秒刷新，`WHERE DATE(created_at)=CURDATE()` |
| Q3 | 待处理订单 | 1.2% | 读 | `WHERE status=0 ORDER BY created_at LIMIT 50` |
| Q4 | 订单详情 | 2.0% | 读 | 先查订单，再循环查商品（N+1 候选） |
| Q5 | 下单 | 0.8% | 写 | INSERT + 2 次 UPDATE |
| Q6 | 支付回调 | 0.5% | 写 | UPDATE 订单状态 |
| — | 其他 | 94% | 混合 | 每次约 2 页随机读 |

### 3.4 增长

```
Registered_{w+1} = Registered_w × (1 + g_organic + g_feature + g_marketing − churn)
```

| 项 | 公式 | 初始 |
|---|---|---|
| `g_organic` | 常数 | 0.028 / 月 |
| `g_feature` | 已交付功能数 × 0.004，上限 0.020 | 0 |
| `g_marketing` | 市场预算 / 8,000,000 | 0.025（20 万预算） |
| `churn` | 0.012 + 3×月度错误率 + latency_penalty | 0.013 |

`latency_penalty = max(0, (p95_ms − 300) / 5000)`，上限 0.02。

年增长约 4~6%/月。要达到 12 个月 35 万注册，需要持续交付 + 稳定运行。

## 4. 数据规模与存储

### 4.1 表

| 表 | 行数（初始） | 行宽 | 说明 |
|---|---|---|---|
| `orders` | 1,200,000 | 320 B | 每月 +84,000 |
| `order_items` | 3,600,000 | 120 B | 每单 3 行 |
| `users` | 200,000 | 480 B | — |
| `payments` | 1,500,000 | 160 B | 每月 +105,000 |

### 4.2 页数

```
rows_per_page = floor(PAGE_BYTES × fill_factor / row_bytes)
P_table = ceil(N / rows_per_page)
P_index = ceil(N / floor(PAGE_BYTES × 0.90 / entry_bytes))
```

`entry_bytes = Σ(列宽) + 8（主键）+ 13（开销）`。

初始（fill=0.72）：`orders` 32,553 页（509MB），`order_items` 36,622 页（572MB），`users` 8,139 页（127MB），`payments` 20,346 页（318MB）；索引 2 个共 7,488 页（117MB）。**合计 105,148 页 / 1.60 GB**。

### 4.3 磁盘

```
disk_used_gb = (ΣP × 16KB) / 2^30
disk_used_pct = disk_used_gb / disk_capacity_gb
```

| 阈值 | 效果 |
|---|---|
| ≥ 80% | 每周告警，运维满意度 −1 |
| ≥ 90% | 写入延迟 ×1.5（页分裂更容易失败） |
| ≥ 100% | 写入直接失败，触发数据丢失风险事件 |

## 5. 查询成本模型

> 这部分是整个游戏的地基。结构参考 InnoDB 的成本模型（CPU 成本 + IO 成本），常数通过真实 MySQL 基准校准。

### 5.1 总公式

```
T(q) = C_parse + T_cpu + T_io
T_cpu = (R × c_row + P_touch × c_page) / 1000          [ms]
T_io  = 顺序扫描: P_touch × (1 − h) × c_seq + w_disk
        随机访问: (P_touch × (1 − h) + P_idx × (1 − h_idx)) × (c_rand + w_disk)
```

| 常数 | 值 | 来源 | 含义 |
|---|---|---|---|
| `C_parse` | 0.12 ms | 待校准 | 解析 + 网络 + 应用开销 |
| `c_row` | 0.06 µs | 待校准 | 扫一行的 CPU |
| `c_page` | 0.20 µs | 待校准 | 访问一页的 CPU |
| `c_rand` | 0.11 ms | 待校准 | 随机读一页 |
| `c_seq` | 0.125 ms | 待校准（128MB/s 吞吐） | 顺序读一页 |
| `h` | 见 §6 | 计算 | Buffer pool 命中率 |
| `h_idx` | 0.98 | 启发式 | 小索引常驻内存 |

### 5.2 访问路径

对每条查询，枚举可能的路径，各算成本，取最小（模拟优化器）：

| 路径 | 条件 | R | P_touch |
|---|---|---|---|
| 全表扫描 | 总是可选 | N | P_table |
| 索引等值 | 索引首列有等值谓词 | N × S_eq | min(P_table, R) |
| 索引范围 | 首列有范围谓词 | N × S_range | min(P_table, R) |
| 覆盖索引 | 查询列 ⊆ 索引列 | R | P_index × S |

`S_eq = 1 / cardinality`（均匀假设）；`S_range = (high − low) / range_width`。

**不模拟**：索引合并（index merge）、多表 join 重排、直方图、统计信息过期。单表查询足够支撑第一版。

### 5.3 排序成本

```
若无索引满足 ORDER BY：
  T_sort = R × log2(R) × c_sort / 1000      [ms]
  c_sort = 0.15 µs
```

`ORDER BY created_at` 在有 `(created_at)` 或 `(user_id, created_at)` 索引时无需排序；否则要 filesort。这是"索引列顺序"最直观的后果。

### 5.4 例子：Q1 的两种路径

`SELECT * FROM orders WHERE user_id=? ORDER BY created_at DESC LIMIT 20`

| 路径 | R | 耗时 | 说明 |
|---|---|---|---|
| 走 `idx_orders_created`（反向扫 + 过滤 user_id） | 1,200,000 | **121 ms** | 用户只有 8 单，扫完整个索引也凑不够 20 条 |
| 走 `(user_id, created_at)` 复合索引 | 20 | **4 ms** | 直接定位，索引序即排序序 |
| 全表扫描 | 1,200,000 | 852 ms | 优化器不会选，但可用 `FORCE INDEX` 强制 |

这个例子的教学点：**"有索引"和"索引对"是两件事**。

## 6. Buffer Pool 与磁盘

### 6.1 命中率

```
W = P_table_total + P_index_total
B = buffer_pool_gb × 2^30 / 16384
h = clamp(1 − exp(−B / (W × 0.75)), 0.30, 0.99)
```

0.75 是热点集中系数（Zipf：20% 的页承接 80% 的访问）。`B/W` 越大，命中率越高，但**收益递减**——这是"加内存"这条路的真实形状。

初始：`W = 105,148`，`B = 131,072`，`h = 0.810`。

### 6.2 磁盘排队

```
D = Σ (QPS_i × io_ops_i)
ρ_disk = D / disk_iops_limit
w_disk = ρ / (disk_iops_limit × (1 − ρ))      当 ρ < 0.995
       = 40 ms（视为饱和）                     当 ρ ≥ 0.995
```

`w_disk` 是**每一次 IO 的平均排队时间**，它会加到所有查询上。这就是"大屏拖垮全站"的机制：不是大屏自己慢，是它把磁盘队列填满了。

### 6.3 为什么是 3,000 IOPS

云盘基线（gp3 3,000 IOPS / 125MB/s）。这是第一版唯一可升级的存储参数：
`disk_iops_limit ∈ {3000, 6000, 12000}`，价格 ¥0 / ¥600 / ¥1800 每月。

## 7. 写入与 DDL

### 7.1 写入成本

```
T_insert = c_write_base + Σ_index (c_index_insert × (1 + bloat))
c_write_base = 1.10 ms
c_index_insert = 0.18 ms
```

初始 1 个索引：1.28ms；加到 5 个：2.00ms。下单 QPS 0.62，影响很小——**这是诚实的**：在这个数据量下，索引对写入的影响不是主要矛盾。真正的代价是磁盘、构建锁和未来的维护复杂度。

### 7.2 建索引

```
build_seconds = N / 30,000            （30k 行/秒，含排序）
```

| 行数 | 朴素 `ALTER`（锁写） | `INPLACE, LOCK=NONE` |
|---|---|---|
| 120 万 | 40 s | 70 s，IO 占用 ×1.6，不阻塞 |
| 500 万 | 167 s | 290 s，IO ×1.6 |
| 2000 万 | 667 s | 1160 s，IO ×1.6 |

**锁写期间的后果**：所有写请求排队，超过 `request_timeout_ms` 的变成 500。写入 QPS × 锁定时长 = 失败请求数。若锁 40 秒、下单 0.62 QPS，约 25 单失败；若在高峰锁 167 秒，约 104 单失败 + 应用队列堆积 → 触发 E02。

### 7.3 索引膨胀

删除导致的空洞：

```
bloat += deleted_rows / N × 0.5
bloat = min(bloat, 0.35)
P_index_eff = P_index × (1 + bloat)
```

`bloat > 0.2` 时提示"索引碎片"，`OPTIMIZE TABLE` 可回收，但要锁表。

## 8. 缓存

### 8.1 命中

TTL 缓存（到期即失效，不做写失效）的命中率近似为"两次过期之间被读到的比例"：

```
h_cache = clamp(1 − 1 / (read_qps × ttl), 0, 0.999)     要求 read_qps × ttl > 1
```

| key | read_qps | ttl | 命中率 |
|---|---|---|---|
| 用户订单列表 | 1.17 | 60s | 0.986 |
| 大屏聚合 | 0.35 | 30s | 0.905 |
| 大屏聚合 | 0.35 | 5s | 0.429 |

单次未命中的成本 = 原查询成本（仍要打 DB），所以缓存对 p95 的改善取决于 `h`；对 p99 的改善几乎为零（未命中的那次仍然慢）。

### 8.2 一致性风险

```
stale_read_rate = bypass_share × (1 − exp(−ttl / refresh_interval))
```

| 参数 | 说明 |
|---|---|
| `bypass_share` | 绕过缓存失效的写入占比（代码属性，初始 0.05） |
| `refresh_interval` | 用户侧刷新间隔（订单状态页 30s，列表页 300s） |

例：TTL 300s，刷新 30s，bypass 5% → `0.05 × (1 − e^-10) ≈ 5%` 的读取看到旧数据。对"支付后状态"来说，5% 已足够引发大量客诉。

**这是启发式，不是推导**：真实系统的不一致取决于失效逻辑的正确性，无法用公式精确表达。这里只保证"方向对、量级可感知"。

### 8.3 缓存击穿

当热点 key 过期且并发高：

```
stampede_qps = 并发等待该 key 的请求数（在 100ms 窗口内的同 key 请求）
```

若 `stampede_qps × 原查询成本` 超过磁盘余量，触发短时尖峰。这个机制让"TTL 设得太整"变成一个真实的坑。

## 9. 连接池

### 9.1 并发需求

```
qps_q_i = QPS_i × queries_per_request_i     （N+1 会把 queries 放大）
λ_db = Σ qps_q_i
s_db_ms = Σ(qps_q_i × T_i) / λ_db
a = λ_db × s_db_ms / 1000                   （爱尔兰，注意单位换成秒）
ρ_pool = a / pool_size
```

### 9.2 等待时间（M/M/c）

```
C(c, a) = Erlang-C
W_p95 = ln(C / 0.05) / (c/s − λ)          （C > 0.05）
      = 0                                  （C ≤ 0.05）
```

若 `W_p95 > pool_timeout_ms`，等待的请求返回 500（`pool timeout`）。

### 9.3 池不是越大越好

| pool | a | ρ | 等待 p95 |
|---|---|---|---|
| 8 | 12.0 | 1.50 | 崩溃 |
| 12 | 12.0 | 1.00 | 崩溃 |
| 16 | 12.0 | 0.75 | 28 ms |
| 24 | 12.0 | 0.50 | ~0 |
| 40 | 12.0 | 0.30 | ~0 |

（`λ=150 QPS`，`s=80ms`）

但 `pool_size > max_connections` 会直接 `Too many connections`；同时数据库侧的上下文切换在 `pool > 64` 后开始拖慢吞吐：

```
db_effective_cores = cores × (1 − min(0.3, max(0, (pool − 64) / 400)))
```

于是存在一个**最优区间**，而不是"越大越好"。

## 10. 应用层

```
workers = servers × workers_per_server          （初始 6 × 8 = 48）
a = λ × s_app
ρ_app = a / workers
W_app_p95 = ln(C / 0.05) / (workers / s_app − λ)
```

`s_app` = 应用处理时间 + 数据库等待 + 缓存等待 + 网络。**注意**：`s_app` 里有 DB 时间，所以数据库变慢会直接吃掉应用容量——这就是死亡螺旋的第一步。

接口 p95：

```
p95_endpoint = s_app_p95 + W_app_p95
```

若 `p95 > request_timeout_ms (1000)` → 该请求计为超时（5xx）。

## 11. 错误与可用性

```
timeout_rate = 超时请求 / 总请求
pool_error_rate = 池超时请求 / 总请求
app_error_rate = 交付质量导致的固定错误率（有测试则低）
error_rate = 1 − (1 − timeout)(1 − pool)(1 − app)
```

```
月度可用性 = 1 − Σ(每周错误请求) / Σ(每周总请求)
```

SLA 目标 99.5%（月）。低于目标：

- 赔偿客户 ¥30,000；
- 王总信任 −10；
- 触发 E02 或 E08 的权重上升。

> 99.5% 意味着每月允许约 3.6 小时不可用。初始状态 99.6~99.8%，看起来"还行"，这正是陷阱。



### 12.3 事件概率

```
p_week = 1 − Π(1 − min(0.35, severity_i × 0.02 × load_factor))
```

| 第 12 月满足 35 万注册 + 60 万收入 + 99.5% | A 轮通过 |

## 15. 职业

```
绩效 = 0.4 × 交付分 + 0.3 × 稳定分 + 0.2 × 技术影响分 + 0.1 × 协作分
```

| 分项 | 计算 |
|---|---|
| 交付 | 按期任务 / 总任务 × 100 |
| 稳定 | min(100, 可用性 / 99.5% × 100) |
| 技术影响 | (期初债 − 期末债) / 期初债 × 100，加成本节省折算 |
| 协作 | 文档 + 复盘 + 帮同事，各 +10，上限 100 |

绩效 → 等级：≥90 S，≥75 A，≥60 B，≥45 C，其余 D。

晋升（第 6、12 月）：平均绩效 ≥ B+ 且至少 1 项"系统所有权"里程碑（独立负责一次故障复盘 / 独立完成一次容量规划 / 独立设计一个被采纳的方案）。

## 17. 参考算例（可复算）

运行 `py -3 tools/refcalc.py` 得到。以下是 M1 初始状态：

### 17.1 规模

- 总页数 105,148 / 1.60 GB / Buffer pool 2GB 下命中率 **0.810**
- DAU 23,994 / 日请求 1,036,541 / 均值 12.0 QPS / 高峰 **78.0 QPS**

### 17.2 场景

| 场景 | 大屏 ms | Q1 ms | IOPS | IO% | 盘等待 ms | 池 ρ | API p95 | 超时 QPS |
|---|---|---|---|---|---|---|---|---|
| M1 现状 | 852 | 121 | 2,224 | 74% | 0.95 | 0.01 | 136 | 0.00 |
| 只加大屏缓存 | 851（命中时 1） | 79 | 266 | 9% | 0.03 | 0.00 | 94 | 0.00 |
| 只改 SQL | 1 | 78 | 63 | 2% | 0.01 | 0.00 | 93 | 0.00 |
| 两样都做 | 1 | 78 | 62 | 2% | 0.01 | 0.00 | 93 | 0.00 |
| M3 拉新后 +35% | 1,050 | 301 | 2,770 | 92% | 4.02 | 0.02 | 316 | 0.35 |
| M4 大促（峰值 ×2.2） | 1,054 | 522 | 2,883 | 96% | 8.20 | 0.05 | 雪崩 | 0.35 |

**读法**：

- M1 的 852ms 里，773ms 是 IO，78ms 是 CPU。**瓶颈是 IO，不是 CPU**——所以"加 CPU"没用，"加内存/改索引"才有用。
- "只加缓存"后，数据库负载降到 14%，但**单次未命中仍是 851ms**。p95 会好看，p99 不会。这就是"缓存掩盖问题"。
- M3 只涨了 35% 用户，Q1 从 121ms 涨到 301ms，API p95 从 136 涨到 316。**非线性**来自磁盘排队（4ms/IO）。这是玩家第一次直观感受到"容量"。
- M4 峰值 ×2.2，应用层直接雪崩（ρ_app > 1），因为单请求要 522ms，48 个 worker 每秒只能处理 92 个请求。

### 17.3 索引对比

| 坏索引（扫 created_at） | 1,200,000 | 121.2 ms |
| 复合索引 `(user_id, created_at)` | 20 | 4.2 ms |

## 18. 不变量

自动化测试必须守住：

1. 任何指标不为 `NaN` / `inf` / 负数。
2. 可用性 ∈ [0, 1]；磁盘使用率 ∈ [0, 1.2]。
3. 给某查询加一个匹配索引，该查询成本**不上升**（允许相等）。
4. 加索引后磁盘占用**不下降**；写入成本**不下降**。
5. 现金变化 = 收入 − 成本 − 一次性支出（除融资），误差 0。
6. 同一 `(seed, actions)` 两次运行，状态哈希相同。
7. 缓存 TTL 增加，命中率**不下降**，陈旧率**不下降**。
8. 服务器增加，应用容量**不下降**，数据库成本**不变**。

## 19. 已知简化（诚实清单）

这些地方**不是**真实物理，别当成真：

| 项 | 简化 | 影响 |
|---|---|---|
| 优化器 | 只比单表访问路径，不做 join 重排、index merge、直方图 | 复杂 SQL 的估计会偏 |
| 缓冲池 | 指数模型 + 热点系数，非真实 LRU | 命中率是近似值 |
| 队列 | M/M/c，假设泊松到达 | 真实流量有自相似性，尖峰更尖 |
| 缓存一致性 | `bypass_share × (1−e^(−ttl/interval))` 启发式 | 只能保证方向对 |
| 网络 | 固定 0.12ms 开销 | 不模拟跨可用区、丢包 |
| 存储 | 均匀 fill_factor | 不模拟行溢出、压缩、页分裂细节 |
| 组织 | 线性满意度模型 | 纯游戏设计，不拟合真实 HR 数据 |
| 经济 | 固定 AOV 和抽佣 | 不模拟定价策略 |

**校准状态**：常数来自 [tools/refcalc.py](tools/refcalc.py) 的初始估计，`tools/bench_mysql.py` 尚未运行。在 M2 阶段会跑真实 MySQL 基准并写入 `content/calibration.json`，届时本表会更新为"已校准"。

## 20. 调参原则

1. **先调结构，再调常数**。如果"加索引没用"，是结构错了，不是常数错了。
2. 改动任何常数，必须重跑 `refcalc.py` 和黄金用例，并在提交信息里写清楚"为什么"。
3. 任何让"某个操作永远最优"的改动，直接拒绝。
4. 任何让"某个操作永远无用"的改动，也拒绝。
5. 数值要让玩家在 3 秒内看懂方向（好/坏），在 30 秒内看懂原因。
